# KPI Sentinel — Project State

_Last updated: end of Milestone 2_

## What We're Building

**KPI Sentinel** — a statistics-first anomaly detection system for e-commerce
KPIs. A student portfolio project designed to look and behave like a real
internal analytics tool.

Core design principle: **statistical/data-science methods detect anomalies;
an LLM only interprets and explains them in business language.** The LLM
never decides what counts as anomalous, and is prompted to avoid asserting
causation it can't support.

Full roadmap (from the original project plan): project setup → synthetic
data → data loading/validation → cleaning → metrics/baselines → anomaly
detection (rolling baseline + z-score, IQR as robustness check, optional
Isolation Forest as a comparison) → cross-metric business rules →
severity scoring → LLM summarization layer → Streamlit dashboard → email
alerts → SQLite alert history → evaluation (precision/recall/F1 +
LLM factuality) → README/portfolio polish.

## Key Facts for Later Milestones

**Dataset columns** (exact names):
`Date, Revenue, Orders, Website_Traffic, Conversion_Rate, Ad_Spend, Refunds, Average_Order_Value`
(the metric is `Average_Order_Value`, not `AOV`).

**Milestone 1 — `generate_synthetic_data.py`**
- `generate_clean_data()` builds 365 days of daily metrics with realistic
  relationships (Orders = Traffic × Conversion_Rate, Revenue = Orders × AOV,
  Refunds as a % of Revenue, Ad_Spend loosely tracking Traffic), weekly
  seasonality, a slow trend, and noise.
- `inject_anomalies()` injects 10 known anomalies (single/multi-day,
  positive/negative, single/multi-metric) and logs them to the ground-truth
  table.
- `RANDOM_SEED = 42`; output is byte-identical on re-run.

**Milestone 2 — loading, validation, cleaning**
- `src/data_loader.py`
  - `load_data(path)` reads .csv/.xlsx/.xls and returns `(df, ValidationReport)`.
    Data is returned exactly as read; nothing is modified.
  - `validate_schema(df)` raises `SchemaError` only if a required column is
    missing. All other problems are warnings: unparseable/duplicate dates,
    missing calendar days, duplicate rows, nulls, non-numeric text,
    negatives, and fewer than `MIN_ROWS = 60` dated rows.
  - Exports `DATE_COLUMN`, `NUMERIC_COLUMNS`, `REQUIRED_COLUMNS`.
- `src/data_cleaning.py`
  - `clean_data(df)` returns `(cleaned_df, CleaningReport)`. Output is one row
    per calendar day, sorted, with a datetime `Date` column and float numeric
    columns. Input is never mutated.
  - Steps in order: parse dates (drop unparseable) → coerce numerics →
    drop duplicate rows → drop duplicate dates (keep first) → reindex to full
    daily calendar → clip negatives to 0 → forward-fill then back-fill blanks.
  - Deliberately never alters extreme-but-real values or genuine zeros;
    judging those is the detector's job.
- `scripts/generate_messy_data.py` corrupts a copy of the Milestone 1 CSV
  (seeded, distinct rows): 5 missing days, 3 duplicate rows, 2 duplicate
  dates, 6 nulls, 3 negatives, 2 text values. Kept separate from business
  anomaly injection on purpose.
- Note: `pd.read_csv` converts the literal text `N/A` to null on read, so
  that defect is reported as a "missing value" rather than "non-numeric".
  The cleaner fills it either way.

## Exact Next Step

Scope and implement **Milestone 3 — metrics/baselines + anomaly detection**,
one small file at a time with tests. Proposed (not yet confirmed) plan:
1. `src/baselines.py` — rolling baseline and z-scores per metric, computed
   from prior days only (current day excluded so an anomaly can't inflate
   its own baseline).
2. `src/anomaly_detection.py` — z-score flagging, IQR as a robustness check,
   per-day/per-metric flags and a combined result table.
3. Tests for both, including cases on known injected anomalies.
4. Optional later: Isolation Forest comparison; scoring against
   `ground_truth_anomalies.csv` belongs to the evaluation milestone.

Open design decision to settle first: the data has weekly seasonality, so a
plain rolling window would flag ordinary weekends. Recommended: a
day-of-week-aware baseline (compare each day with the same weekday over the
previous several weeks).

# KPI Sentinel — Project State

_Last updated: Milestones 4 and 5 implemented; awaiting local verification_

## What We're Building

**KPI Sentinel** — a statistics-first anomaly detection system for e-commerce
KPIs. A student portfolio project (UMD Information Science, targeting data
analyst / data science roles) designed to look and behave like a real
internal analytics tool.

Core design principle: **statistical/data-science methods detect anomalies;
an LLM only interprets and explains them in business language.** The LLM
never decides what counts as anomalous, and is prompted to avoid asserting
causation it can't support.

Full roadmap (from the original project plan): project setup → synthetic
data → data loading/validation → cleaning → metrics/baselines → anomaly
detection (rolling baseline + z-score, IQR as robustness check, optional
Isolation Forest as a comparison) → cross-metric business rules →
severity scoring → LLM summarization layer → Streamlit dashboard → email
alerts → SQLite alert history → evaluation (precision/recall/F1 + LLM
factuality) → README/portfolio polish.

## Key Facts for Later Milestones

**Dataset columns** (exact names):
`Date, Revenue, Orders, Website_Traffic, Conversion_Rate, Ad_Spend, Refunds, Average_Order_Value`
(the metric is `Average_Order_Value`, not `AOV`).

**Ground truth schema** (`ground_truth_anomalies.csv`):
`start_date, end_date, duration_days, metrics_affected, anomaly_type, description`.
10 events (5 single-day, 5 sustained multi-day), 60 labelled
(day, metric) cells. `metrics_affected` is a comma-separated string.
Event types: conversion collapse; traffic spike with no order lift (traffic
quality); sustained conversion drop; refund spike; ad-spend surge with only
modest revenue growth (marketing efficiency); sustained traffic drop;
AOV spike; positive demand spike (all of traffic/conversion/orders/revenue
up); sustained elevated refunds; broad purchasing-behaviour decline with
stable traffic.

**Milestone 1 — `generate_synthetic_data.py`**
- `generate_clean_data()` builds 365 days of daily metrics with realistic
  relationships (Orders = Traffic x Conversion_Rate, Revenue = Orders x AOV,
  Refunds as a % of Revenue, Ad_Spend loosely tracking Traffic), weekly
  seasonality, a slow trend, and noise. `inject_anomalies()` injects the 10
  known anomalies. `RANDOM_SEED = 42`; output is byte-identical on re-run.

**Milestone 2 — loading, validation, cleaning**
- `load_data(path)` -> `(df, ValidationReport)`; returns data as read.
  `validate_schema` raises `SchemaError` only for missing required columns;
  everything else is a warning. `MIN_ROWS = 60`.
- `clean_data(df)` -> `(cleaned_df, CleaningReport)`: one row per calendar
  day, sorted, datetime `Date`, float numeric columns. Never alters
  extreme-but-real values or genuine zeros.
- `generate_messy_data.py` corrupts a copy of the data for testing.
- Note: `pd.read_csv` turns literal `N/A` into null, so it is reported as a
  missing value rather than non-numeric; the cleaner fills it either way.

**Milestone 3 — baselines, detection, evaluation**
- `src/baselines.py`: `compute_baselines(df, metrics=None, window_weeks=8)`
  returns one row per day x metric: `Date, Metric, Value, Baseline_Mean,
  Baseline_Std (ddof=1), Baseline_Q1, Baseline_Q3, Z_Score`. Baseline = same
  weekday over the previous `window_weeks` weeks, prior days only (the
  current day never contaminates its own baseline). Requires `clean_data`
  output (one row per day). The first `7 * window_weeks` days (56 by default)
  have no baseline (NaN). `Z_Score` is NaN when baseline std is 0.
- `src/anomaly_detection.py`: `detect_anomalies(baselines, z_threshold=4.0,
  iqr_multiplier=1.5)` adds `IQR_Lower, IQR_Upper, Z_Flag, IQR_Flag,
  Is_Anomaly, Direction`. `Is_Anomaly` = |z| > threshold AND outside IQR
  fences. Direction is "spike"/"drop" for anomalies. Rows with no baseline
  are never flagged.
- `src/evaluation.py`: `load_ground_truth`, `expand_labels` (event -> one row
  per Event_ID/Date/Metric), `score_detections(detections, labels,
  window_weeks)` -> `(summary_dict, per_event_df)`. Scores at (day, metric)
  level, excludes warm-up cells, and counts "echo" false positives (same
  metric, 1..window weeks after a labelled cell).
- `scripts/evaluate_detection.py` sweeps window (4, 8) x z (3, 4, 5).

**Milestone 4 — derived metrics, incidents, business rules**
- `src/derived_metrics.py`: `add_derived_metrics(df)` adds `Refund_Rate`
  (Refunds / Revenue) and `Revenue_per_Ad_Dollar` (Revenue / Ad_Spend);
  zero/negative denominators give NaN. `ALL_METRICS` = 7 raw + 2 derived.
  Ratios are supporting evidence: a flag on a ratio can be a mechanical
  side effect (Refund_Rate rises when Revenue collapses).
- `src/incidents.py`: `build_incidents(detections, max_gap_days=1)` groups
  flagged cells on consecutive days (all metrics) into incidents. Columns:
  `Incident_ID, Start_Date, End_Date, Duration_Days, Metrics,
  Metric_Directions (metric -> spike/drop/mixed), N_Flagged_Cells, Peak_Abs_Z`.
- `src/business_rules.py`: `classify_incidents(incidents)` adds `Category,
  Impact, Pattern, Evidence`. First matching rule wins, in this order:
  demand_spike (positive) -> marketing_efficiency -> traffic_quality ->
  conversion_drop -> traffic_drop -> refund_issue -> aov_spike (positive) ->
  unclassified. Descriptions are hedged ("consistent with ...") and never
  assert causation. Rules label incidents; they never decide what is anomalous.
- `src/evaluation.py` gained `score_incidents(incidents, ground_truth,
  tolerance_days=1)`: event-level scoring (does any incident overlap each
  ground-truth event?), which credits incidents built from any metric,
  including derived ratios.

**Milestone 5 — severity**
- `src/severity.py`: `score_incidents(incidents)` adds `Severity_Score`
  (0-100), `Severity_Label` (Low <35, Medium <55, High <75, Critical) and
  `Severity_Breakdown`. Points: magnitude 40 (peak |z|, cap 10), breadth 20
  (raw metrics only, cap 4), duration 15 (cap 5 days), revenue 25 (drop 25,
  mixed 15, spike 10). A weak single-raw-metric incident (|z| < 8) is x0.6;
  positive-impact incidents are x0.6. Weights and cut-offs are transparent
  heuristics, not statistically derived.
- Sandbox check (synthetic noise, 30 seeds): noise incidents had median
  severity 15.7, 95th percentile 39.9, and 1.1% reached High; an injected
  conversion drop scored 83 (Critical). This is not a real-data result.
- `src/pipeline.py`: `run_detection_pipeline(cleaned)` -> `(detections,
  incidents)` runs derived metrics -> baselines -> detection -> incidents ->
  rules -> severity. `scripts/run_pipeline.py` runs it on the real data,
  writes `data/processed/incidents.csv`, prints the top incidents and an
  event-level comparison with the ground truth.

Design lessons recorded during development: a first severity version gave
any lone Revenue drop 25 revenue points (noise incidents reached High);
fixed by counting only raw metrics for breadth and damping weak single-
metric flags. The first rule order labelled the ad-spend event as
traffic_quality (traffic also rose); fixed by ordering marketing_efficiency
first.

## Evaluation Results (real project data)

| window | z | precision | recall | F1 | TP | FP | FN | events | echo FP | unscorable |
|---|---|---|---|---|---|---|---|---|---|---|
| 4 | 3 | 0.23 | 0.82 | 0.36 | 49 | 161 | 11 | 10/10 | 0 | 0 |
| 4 | 4 | 0.34 | 0.72 | 0.46 | 43 | 83 | 17 | 10/10 | 0 | 0 |
| 4 | 5 | 0.45 | 0.62 | 0.52 | 37 | 46 | 23 | 9/10 | 0 | 0 |
| 8 | 3 | 0.53 | 0.82 | 0.64 | 47 | 42 | 10 | 9/9 | 1 | 3 |
| **8** | **4** | **0.77** | **0.77** | **0.77** | 44 | 13 | 13 | 9/9 | 1 | 3 |
| 8 | 5 | 0.92 | 0.63 | 0.75 | 36 | 3 | 21 | 9/9 | 0 | 3 |

- **Chosen defaults: 8-week window, |z| > 4** (best F1; balanced precision
  and recall). Now set as `WINDOW_WEEKS = 8` and `Z_THRESHOLD = 4.0`.
- Window length mattered most: at z > 4, F1 0.46 (4 weeks) vs 0.77 (8 weeks).
  Simulation on pure noise agreed: 4-sample baselines flag ~7% of normal
  days at |z| > 3; 8-sample baselines ~2.5%. Requiring IQR agreement barely
  changed false positives (7.29% -> 7.22% in simulation), so it is a minor
  guard, not the main control.
- Event 1 (2025-11-01, 3 cells) falls inside the 8-week warm-up and is
  unscorable with an 8-week window (a cold-start cost: the first 56 days are
  not monitored). A 4-week window did detect it.
- Echo false positives are ~1, so baseline contamination from past
  anomalies is not currently a problem; no robust (median/MAD) baseline
  needed yet.
- Weakest events at 8 weeks / z > 4: event 5 (Mar 14-18, ad-spend surge /
  marketing efficiency; 7 of 15 cells), event 9 (Jul 25-28, sustained
  refunds; 2 of 4), event 10 (Aug 28-30, broad decline; 6 of 9). These are
  sustained or modest-effect events; ratio-based signals (revenue per ad
  dollar, refund rate) and cross-metric rules are the intended fix.
